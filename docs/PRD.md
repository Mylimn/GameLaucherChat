# PRD — 游戏启动器 + 实时聊天 桌面客户端

> 版本：v0.3（新增 UI 深色现代风格要求；文档迁入 docs/）
> 状态：待评审
> 关联文档：[TECH_DESIGN.md](./TECH_DESIGN.md)、[AGENTS.md](../AGENTS.md)、[DEVLOG.md](./DEVLOG.md)

## 1. 背景与目标

### 1.1 背景

用户将**手动开发一个 C++ 服务端**（提供本地游戏联动 + 实时聊天能力）。在服务端成型之前，缺少一个对端来进行协议联调、验证设计，也无法在服务端尚未完成时体验完整链路。

因此先开发一个 **Windows 桌面客户端**，并配套一个**轻量 mock 服务端**：客户端面向真实功能设计，协议接口先定死，mock 服务端用于联调；后续用户手写的服务端只需按协议实现即可无缝替换 mock。

### 1.2 目标

- 交付一个 Qt 6 / C++ 桌面客户端，具备两大能力：
  1. **本地游戏启动器**：从本地列表拉起游戏进程并跟踪运行状态。
  2. **实时聊天**：私聊 + 好友列表（含添加/处理请求、在线状态、离线消息、历史记录）。
- 交付**账号体系**：客户端自助注册、服务端 SQLite 持久化、密码加盐哈希（不存明文）。
- 交付一个轻量 mock 服务端（C++ 可执行），与客户端**共用同一份协议定义**。
- 协议定义集中、清晰、可扩展，作为客户端与服务端之间的**契约**。

### 1.3 非目标（本期不做）

- 群聊 / 多人群组、频道
- 图片、文件、语音、视频消息
- 消息加密、端到端安全
- 多端同步、消息漫游到多设备
- 公网部署、账号找回（找回密码 / 邮箱验证 / 第三方登录）
- 服务端管理后台

> 注：**账号自助注册、账号/好友/消息的 SQLite 持久化、密码加盐哈希**已纳入本期（见 §3.1）。

> 说明：以上非目标在协议与架构上预留扩展位，但不在本期实现。

## 2. 用户角色与使用场景

### 2.1 用户角色

| 角色 | 说明 |
|---|---|
| 使用者（玩家） | 在本机登录客户端，查看好友、收发私聊、从游戏库启动本地游戏 |
| 开发者（用户本人） | 以客户端为对端基准，手写服务端的协议实现；mock 服务端为其提供参考实现 |

### 2.2 核心场景

1. **注册与登录**
   首次使用：登录页切到「注册」→ 输入用户名 / 显示名 / 密码 → 服务端校验用户名唯一 → 创建账号 → 返回登录页并使用新账号登录。
   已有账号：输入用户名 / 密码 → 连接服务端 → 登录成功 → 拉取好友列表与在线状态。
2. **加好友与聊天**
   添加好友 → 对方（mock 中为另一客户端实例）收到请求 → 接受 → 双方互为好友 → 私聊互发消息 → 离线期间消息在下次登录补推。
3. **启动本地游戏**
   在游戏库选中游戏 → 点击启动 → 拉起本地进程 → 面板显示「运行中」→ 退出游戏后状态变为「已退出」→ 支持手动结束进程。

## 4. 非功能需求（NFR）

| 编号 | 需求 |
|---|---|
| NFR-1 | **平台**：Windows 10/11 x64 |
| NFR-2 | **技术栈**：C++20 + Qt 6.12（Widgets）、CMake 构建、MSVC 2022 编译 |
| NFR-3 | **性能**：本机连接建立 < 1s；消息端到端延迟 < 100ms（本机） |
| NFR-4 | **稳定性**：服务端不可用、网络中断、游戏 exe 缺失等异常场景不崩溃、不卡 UI 线程 |
| NFR-5 | **可维护性**：协议定义集中在 `shared/`，客户端与 mock 服务端共用；文档与代码保持同步 |
| NFR-6 | **线程安全**：网络 I/O 与 UI 分离，UI 不因网络阻塞 |
| NFR-7 | **安全（本期弱约束）**：密码**加盐哈希**存储（不落明文）；传输仍为明文（仅本机联调），**公网使用前必须加固 TLS**（见 TECH_DESIGN 待办） |
| NFR-8 | **数据持久化**：账号、好友关系、消息由服务端用 SQLite 落盘，服务端重启后数据不丢失 |
| NFR-9 | **界面风格**：统一的**深色现代风格**——卡片化分区、圆角、留白充足、单一主色强调；颜色集中定义、通过 QSS 统一皮肤，不在 UI 代码散落硬编码颜色（规范见 TECH_DESIGN §7） |
| NFR-10 | **界面一致性**：所有控件须呈现 hover / pressed / disabled / focus 状态；列表项、消息气泡、连接状态点遵循同一套视觉语言；不得出现未换肤的原生灰色控件 |

## 6. 验收标准

在本机同时运行 `mock_server` 与两个客户端实例，可完整走通：

1. 客户端自助注册两个新账号并分别登录成功；重启 mock 服务端后，账号、好友、消息仍然存在（SQLite 落盘）；
2. A 添加 B 为好友，B 收到请求并接受；
3. A、B 互发私聊消息，实时到达；
4. B 下线后 A 继续发消息，B 重新登录后收到离线消息；
5. 客户端可启动一个本地游戏 exe，并正确显示运行状态、可结束进程；
6. 客户端可通过「添加游戏」导入一个本地 exe，重启客户端后该条目仍在，且可从库中移除；
7. 关闭并重启 mock 服务端后，客户端能自动重连（登录态失效则回到登录页）；
8. 界面呈现统一深色主题：颜色、圆角、间距一致，交互状态（hover / 选中 / 禁用）反馈正常。

## 7. 待确认 / 风险

- 游戏库封面图资源来源（本地图片 vs 服务端下发）——本期用本地图片路径，缺省显示首字母占位。
- 游戏库配置文件位置——`%APPDATA%\GameLauncherChat\games-<userId>.json`，按账号隔离；若用户手动改坏 JSON，客户端只提示不覆盖，避免丢数据。
- 账号体系范围：本期 = 客户端自助注册 + SQLite 持久化 + 密码加盐哈希；找回密码、邮箱验证、第三方登录不做。
- 密码哈希强度：MVP 用「随机盐 + SHA-256」；公网前应升级为 PBKDF2/bcrypt 类慢哈希（见 TECH_DESIGN §12）。
- 消息顺序与去重策略的严格程度——本期按「单连接内顺序投递 + serverMsgId 去重」实现。
